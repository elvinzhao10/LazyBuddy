# Lazyworkbuddy v0.13 — optional add-ons

These add-ons build on top of v0.7+ and are optional. Use them only after the core plugin, state ledger, commands, and verification loop exist.

---

Optional add-on prompt — workbuddy automation runner

Use this only after v0.7 or later, because workbuddy’s SDK/headless automation needs explicit configuration. The Agent SDK documentation says SDK runs do not automatically load filesystem configs such as settings.json, workbuddy.md, MCP servers, subagents, slash commands, Rules, or Skills unless settingSources is explicitly configured, so this should be treated as a controlled automation wrapper, not the default user path.  

Lazyworkbuddy automation add-on — Build a controlled headless/SDK runner.
Use this only after the Lazyworkbuddy plugin, state ledger, commands, and verification loop exist.
Objective:
Create an optional automation runner for Lazyworkbuddy that can run bounded workflows programmatically.
Implement one of these approaches, choosing the most appropriate for this workspace:
A. Headless CLI runner
- scripts/lazyworkbuddy-headless-run.*
- Uses workbuddy -p or equivalent.
- Uses conservative allowedTools.
- Uses explicit permission mode.
- Does not use dangerous skip permissions except in trusted sandboxed CI.
- Writes all run output to .lazyworkbuddy/runs/<run_id>/.
B. HTTP API runner
- scripts/lazyworkbuddy-http-runner.*
- Starts or connects to workbuddy --serve.
- Uses REST or ACP only for controlled tasks.
- Saves request/response summaries.
C. Agent SDK runner
- scripts/lazyworkbuddy-sdk-runner.*
- Explicitly loads settingSources if using project settings/rules/skills.
- Explicitly configures MCP servers if needed.
- Implements canUseTool or equivalent permission guard.
- Enforces resource limits and timeout.
- Saves outputs and checkpoints.
Required behavior:
- No hidden state.
- No silent permission bypass.
- No unbounded loops.
- Every cycle writes state, events, verification, and review.
- Automation must stop on blocker, failed hard gate, budget limit, or required approval.
Required docs:
- docs/lazyworkbuddy-automation-runner.md
- docs/lazyworkbuddy-headless-security.md
- docs/lazyworkbuddy-ci-usage.md
Verification:
- Run a documentation-only automation task.
- Confirm state ledger is updated.
- Confirm verifier runs.
- Confirm reviewer decision is recorded.
- Confirm automation stops safely on failed verification.
- Confirm runner can resume a run from state.
Required output:
- Runner type selected and why
- What I inspected
- What I found
- What I changed
- How to run it
- Verification performed
- Remaining gaps

Optional add-on prompt — Channels and remote-control status

Use this only if you want Lazyworkbuddy to feel closer to WorkBuddy-style remote operation. workbuddy Channels are documented as MCP-backed bridges that can push external messages into running sessions, support two-way chat behavior, and include WeChat, Telegram, and Discord, but events arrive only while a session is open unless workbuddy is run persistently.  

Lazyworkbuddy remote add-on — Add Channels-based status and approval flow.
Objective:
Allow a developer to monitor and control Lazyworkbuddy runs from supported workbuddy Channels.
Implement remote commands:
- status <run_id>
- resume <run_id>
- pause <run_id>
- cancel <run_id>
- approve <approval_id>
- reject <approval_id> <reason>
- verify <run_id>
- final-report <run_id>
Required behavior:
- Channel messages never bypass permissions.
- Approval commands write approval records to .lazyworkbuddy/runs/<run_id>/events.jsonl.
- Remote status reads from state.json, not chat memory.
- External channel replies summarize only safe information.
- Sensitive file paths or secret-like values are redacted.
- Long-running remote use requires a persistent workbuddy session or background process.
Required artifacts:
- docs/lazyworkbuddy-remote-control.md
- docs/lazyworkbuddy-approval-flow.md
- lazyworkbuddy-plugin/mcp/remote-control/ if needed
- lazyworkbuddy-plugin/commands/status.md updated
- lazyworkbuddy-plugin/commands/approve.md if command support is useful
- lazyworkbuddy-plugin/commands/reject.md if command support is useful
Verification:
- Simulate status request.
- Simulate approval request.
- Simulate approval rejection.
- Confirm events are recorded.
- Confirm state changes are deterministic.
- Confirm no sensitive content is sent over channel.
Required output:
- Remote feature status
- What I inspected
- What I found
- What I changed
- How to run it
- Verification performed
- Remaining gaps

Optional add-on prompt — MCP Apps dashboard

Use this if you want a richer UI. workbuddy’s MCP Apps support lets MCP tools associate with sandboxed HTML widgets; reverse tool calls from the widget require user authorization, which is useful for a read-mostly Lazyworkbuddy run dashboard.  

Lazyworkbuddy dashboard add-on — Build an MCP Apps run dashboard.
Objective:
Create a read-only-first dashboard for Lazyworkbuddy run state, parity coverage, and verification gates.
Dashboard views:
1. Active run summary
2. Task graph
3. Verification gates
4. Reviewer decision
5. Changed files
6. Parity coverage
7. Known gaps
8. Pending approvals
9. Latest events
10. Final report links
Rules:
- Dashboard is read-only by default.
- Any state-changing action requires explicit user authorization.
- Dashboard must not display secrets.
- Dashboard must degrade gracefully to Markdown status if MCP Apps are unavailable.
Required artifacts:
- lazyworkbuddy-plugin/mcp/status-dashboard/
- lazyworkbuddy-plugin/mcp/status-dashboard/widget.html
- lazyworkbuddy-plugin/mcp/status-dashboard/server.*
- docs/lazyworkbuddy-dashboard-design.md
- docs/lazyworkbuddy-dashboard-security.md
Verification:
- Render dashboard if supported.
- Confirm task graph data comes from state.json.
- Confirm verification data comes from verification/*.json.
- Confirm write-back actions are authorization-gated.
- Confirm fallback Markdown status works.
Required output:
- Dashboard status
- What I inspected
- What I found
- What I changed
- How to run it
- Verification performed
- Remaining gaps
