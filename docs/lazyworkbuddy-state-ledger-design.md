# Lazyworkbuddy State Ledger Design

> v0.1 — `.lazyworkbuddy/runs/<run_id>/` schema, loop protocol, checkpoint rules

## Overview

The state ledger is the durable progress system that enables resumable autonomous runs. It mirrors LazyCodex's `.omo/` directory but uses WorkBuddy-native conventions and adds checkpointing for resilience.

**LazyCodex source:**
- `.omo/boulder.json`: [start-work SKILL.md](../dev/reference/lazycodex/plugins/omo/skills/start-work/SKILL.md) Phase 2, lines 72-90
- `.omo/start-work/ledger.jsonl`: Phase 4, lines 128-130
- Sisyphus completion contract: Phase 4, lines 132-161 (DoneClaim, AdversarialVerify, FullyDone)
- `.omo/plans/`: [ulw-plan SKILL.md](../dev/reference/lazycodex/plugins/omo/skills/ulw-plan/SKILL.md) — scaffolded plan files
- `.omo/ulw-loop/`: [ulw-loop SKILL.md](../dev/reference/lazycodex/plugins/omo/skills/ulw-loop/SKILL.md) — CLI-managed goal state

## Directory Structure

```
.lazyworkbuddy/
├── runs/
│   └── <run_id>/                    # One directory per autonomous run
│       ├── state.json               # Active work state (boulder.json equiv)
│       ├── events.jsonl             # Evidence ledger (ledger.jsonl equiv)
│       ├── checkpoints/             # Periodic state snapshots
│       │   ├── cp-001/              # Checkpoint after 5th checkbox
│       │   │   ├── state.json       # state.json at checkpoint time
│       │   │   └── manifest.json    # Checkpoint metadata
│       │   └── cp-002/              # Checkpoint after 10th checkbox
│       └── evidence/                # QA artifacts, screenshots, logs
│           ├── <task-001>/
│           ├── <task-002>/
│           └── ...
├── plans/                           # .omo/plans/ equiv
│   └── <slug>.md                    # Decision-complete work plan
├── context/                         # Generated by init-deep
│   └── index.json                   # Context index for agents
└── ulw-loop/                        # UWL loop goal state
    └── <session-id>/
        ├── goals.json               # Loop goal definitions
        └── evidence/                # Per-goal evidence
```

### Field Mapping from LazyCodex

| LazyCodex boulder.json | Lazyworkbuddy state.json | Notes |
|------------------------|--------------------------|-------|
| `schema_version: 2` | `schema_version: 2` | Same schema version pattern |
| `active_work_id` | `run_id` | Namespaced to run |
| `works.<id>.active_plan` | `plan_reference` | Relative path to plan |
| `works.<id>.plan_name` | `plan_name` | Short name for display |
| `works.<id>.session_ids` | `session_ids` | Array of session IDs |
| `works.<id>.status` | `status` | active/paused/completed/failed/aborted |
| `works.<id>.worktree_path` | `worktree.path` | Null if not using worktrees |
| (implicit) | `progress` | Added: explicit progress tracking |
| (implicit) | `iteration` | Added: iteration count + cap |
| (implicit) | `tier` | Added: LIGHT/HEAVY + justification |
| (implicit) | `checkpoints` | Added: checkpoint tracking |
| (implicit) | `checkboxes[]` | Added: per-checkbox state with DoneClaim + AdversarialVerify |

**LazyCodex source:** Boulder state schema in [start-work SKILL.md](../dev/reference/lazycodex/plugins/omo/skills/start-work/SKILL.md) lines 75-89.

### State Transitions

```
                ┌──────────┐
     create ──► │  active  │
                └────┬─────┘
                     │
         ┌───────────┼───────────┐
         ▼           ▼           ▼
    ┌────────┐  ┌─────────┐  ┌────────┐
    │ paused │  │ failed  │  │completed│
    └───┬────┘  └─────────┘  └────────┘
        │
        ▼
    ┌────────┐
    │ active │  (resume)
    └────────┘

    Any state ──► aborted (user-initiated)
```

## events.jsonl Format

### Schema

Each line is a JSON object. Events are **append-only** — never modify existing lines.

```jsonc
{
  "event": "done_claim",           // Event type
  "timestamp": "2026-07-09T12:15:00+08:00",
  "run_id": "run-20260709-001",
  "session_id": "session-abc123",
  "checkbox_index": 0,
  "plan": ".lazyworkbuddy/plans/login-form.md",
  "task": "create-login-form",
  "actor": "subagent-xyz",         // Who performed the action
  "data": {
    // Event-type-specific payload
  }
}
```

### Event Types

| Event Type | When Emitted | Payload |
|------------|-------------|---------|
| `run_created` | Phase 2: boulder state created | plan_reference, plan_name, tier |
| `checkbox_started` | Work begins on a checkbox | checkbox_index, task, implementer |
| `done_claim` | Subagent claims completion | changed_files, tests, manual_qa, cleanup, risks |
| `adversarial_verify` | Verifier checks done claim | verdict (confirmed/false-positive/needs-fix/needs-human-review), evidence, repro, confidence |
| `fully_done` | DoneClaim + AdversarialVerify confirmed | checkbox_index |
| `checkbox_completed` | All 5 gates passed | checkbox_index, summary |
| `task_failed` | Implementation or verification failed | error, stack_trace (redacted) |
| `review_lane_pass` | One review lane passed | lane_number, lane_name, confidence |
| `review_lane_fail` | One review lane failed | lane_number, lane_name, blocking_issues |
| `review_aggregate` | All 5 lanes complete | verdict (PASS/FAIL/INCONCLUSIVE), per-lane results |
| `checkpoint_created` | Checkpoint snapshot taken | checkpoint_id, checkbox_index |
| `checkpoint_restored` | Run restored from checkpoint | checkpoint_id, restored_at |
| `run_paused` | Run paused by user or error | reason |
| `run_resumed` | Run resumed from paused | resumed_by |
| `run_completed` | All checkboxes done + review passed | final_verification_results |
| `run_failed` | Run cannot continue | failure_reason |
| `run_aborted` | User aborted the run | aborted_by |

**LazyCodex source:** Ledger events described in [start-work SKILL.md](../dev/reference/lazycodex/plugins/omo/skills/start-work/SKILL.md) Phase 4 (lines 128-130) and Sisyphus completion contract (lines 132-161).

## Checkpoint Protocol

### When to Checkpoint

Checkpoints are created automatically after every N completed checkboxes (default: N=5). A checkpoint is also created:
- Before any destructive action (major refactor, data migration)
- When the run is paused (user-initiated or error)
- Before context compaction (PreCompact hook)

### Checkpoint Contents

```
.lazyworkbuddy/runs/<run_id>/checkpoints/cp-003/
├── state.json              # Full state.json at checkpoint time
└── manifest.json           # Checkpoint metadata
```

```jsonc
// manifest.json
{
  "checkpoint_id": "cp-003",
  "run_id": "run-20260709-001",
  "created_at": "2026-07-09T13:00:00+08:00",
  "checkbox_index": 15,
  "completion_percentage": 75.0,
  "reason": "auto",                // auto | pre_destructive | paused | pre_compact
  "event_count": 47,               // Number of events in events.jsonl at checkpoint
  "plan_sha": "abc123def456",      // SHA of plan file at checkpoint
  "checksum": "sha256:..."         // Checksum of state.json for integrity
}
```

### Restore Protocol

```
1. Read checkpoint manifest → verify checksum
2. Copy state.json from checkpoint → .lazyworkbuddy/runs/<run_id>/state.json
3. Truncate events.jsonl to event_count from manifest (or preserve all — checkpoint is informational)
4. Read plan file from plan_reference
5. Resume from checkbox_index + 1 (first unchecked checkbox)
6. Log checkpoint_restored event to events.jsonl
7. Continue with Phase 3 (execute next checkbox)
```

### Checkpoint Rotation

- Keep last 3 checkpoints; delete older ones
- On run completion: keep only the final state.json; delete all checkpoints
- On run failure: keep all checkpoints for debugging

## Loop Protocol

### Ultrawork Mode (500 iteration cap)

```
LOOP:
  1. Read state.json → find first unchecked checkbox (status: pending or in_progress)
  2. If no unchecked checkboxes: exit loop → Phase 5 (completion)
  3. Classify tier (LIGHT/HEAVY) for this checkbox
  4. Decompose into atomic sub-tasks
  5. Dispatch sub-tasks to implementer agents
  6. Wait for all sub-tasks to complete (or timeout)
  7. For each completed sub-task:
     a. Collect DoneClaim from implementer
     b. Run AdversarialVerify (independent verifier)
     c. If confirmed → mark FullyDone → update checkbox to completed
     d. If not confirmed → re-dispatch with feedback
  8. Increment iteration count
  9. If iteration_count >= 500: exit loop → mark run as incomplete
  10. If checkbox_index is multiple of checkpoint_frequency: create checkpoint
  11. GOTO 1
```

**LazyCodex source:** Iteration caps of 500 (ultrawork mode) / 100 (normal mode) are documented in the [README.md](../dev/reference/lazycodex/README.md) Commands table for `$ulw-loop`: "Caps at 500 iterations in ultrawork mode, 100 in normal mode." Note: this is an *iteration* cap on the verification loop, distinct from ultrawork's *goal budget* rule ([ultrawork SKILL.md](../dev/reference/lazycodex/plugins/omo/skills/ultrawork/SKILL.md): "Goals are unlimited; never invent a numeric budget or limit") — the two are different concepts and must not be conflated.

### Normal Mode (100 iteration cap)

Same as Ultrawork, but cap at 100 iterations and simpler verification (no adversarial class probing).

### Loop Health Checks

The loop monitor checks for:
- **Stall detection:** No progress for 10+ iterations → warn, then abort after 20
- **Checkbox regression:** Previously completed checkbox found unchecked → restore from checkpoint
- **State corruption:** state.json unreadable → restore from latest checkpoint; if no checkpoint, abort
- **Timeout:** Total run wall-clock time exceeds configurable maximum → pause and ask user

## File Access Conventions

### Who Writes What

| File | Writer | Mode | Locking |
|------|--------|------|---------|
| `state.json` | Orchestrator only | Write (overwrite) | Single-writer; no concurrent access |
| `events.jsonl` | Orchestrator + Verifier | Append-only | Atomic append (O_APPEND) |
| `checkpoints/` | Orchestrator only | Write (create directory + files) | Created after state.json write |
| `evidence/` | Any agent (scoped) | Write (create files) | Per-task subdirectory |
| `plans/<slug>.md` | Planner only | Write (create + edit) | Scaffolded by script; todos appended |

### Why single-writer for state.json?

**LazyCodex pattern:** The orchestrator (Sisyphus) is the sole coordinator. Subagents report back but never write to shared state. This avoids race conditions and keeps the state model simple.

**Our implementation:** Only the orchestrator writes `state.json`. Subagents communicate results via their agent output, which the orchestrator reads and records. Verifier writes evidence to `events.jsonl` (append-only, race-safe).

## Garbage Collection

- **Active runs:** Created on `/lazy-start-work`, garbage collected on completion or abort
- **Completed runs:** State preserved for 30 days after completion; then compressed and moved to archive
- **Abandoned runs:** State older than 7 days with no activity → marked as `aborted`
- **Checkpoints:** Last 3 kept; older deleted
- **Evidence files:** Kept with run; deleted when run is garbage collected
- **Plan files:** Kept indefinitely (reference material)
