# v1.0.3 Adaptive Harness — Change Map

## Overview

LazyBuddy v1.0.3 extends — never replaces — the existing execution substrate. The adaptive harness is a thin layer that maps one behavior-only decision contract (shared with LazyTrae) onto LazyBuddy's existing detector, capability broker, orchestrator, run-ledger state, status-dashboard MCP, and verifier. Every seam listed below already exists at v1.0.2 and continues to do its current job after v1.0.3; the adapter adds an adaptive decision path that selects and composes those surfaces. No source file is replaced, no new MCP server is introduced, no new command is registered, and the single-writer `adaptive` snapshot rides on the existing atomic state scripts.

## Seams

### 1. Request detection
- **File:** `lazybuddy-plugin/tooling/lazybuddy_detector.py`
- **Current behavior:** A 230-line Python CLI with two subcommands: `detect` and `fallback`. `detect` reads a JSON `TaskContext` (`question`, `alreadyTriedLocal`), gathers `repository_facts` (languages, package files, source-file count, git state), then calls `detect_capability()` — a first-match ordered classifier that returns `(capability, reason, evidence)`. Today's capability vocabulary is the v1.1.0 contract set: `local_search`, `browser_automation`, `architecture_search`, `documentation_search`, `external_code_search`. Secrets are scrubbed via `bounded_query()` (Authorization bearer, `api_key=…`, etc.). `fallback` walks the contract-declared `fallbacks` chain and emits `complete | fallback | denied | unavailable` outcomes.
- **Exports/API:**
  - `detect_capability(context: TaskContext, facts: dict) -> tuple[str, str, list[str]]`
  - `fallback_chain(capability: str, contract: dict) -> list[str]`
  - `parse_context(raw: str) -> TaskContext` (validates `{question, alreadyTriedLocal}` shape)
  - `canonical_capability(raw, contract)` and `LEGACY_CAPABILITIES` alias map
  - `read_contract()` (sha256-verified loader shared with the rest of `tooling/`)
  - CLI: `lazybuddy_detector.py detect --workspace <dir> --context-json <json>` / `fallback <capability> --outcomes-json <json>`
- **Workflow-mode classification:** None today. The detector emits a single `capability` string plus `reason`/`evidence`. There is no concept of `mode`, `stages`, `responsibilities`, `escalationCount`, or `approvalRequired`.
- **Extension strategy (W3.1):** Add a new `detect_adaptive()` function (and CLI subcommand `detect-adaptive`) that reuses `parse_context`, `repository_facts`, `bounded_query`, `read_contract`, and the existing secret-scrubbing. It gathers all signals first, then applies the Section 6 ordered policy (explicit → continuation → long-horizon → orchestrated → planned → assisted → direct) and emits the Section 5 decision shape `{mode, stages, responsibilities, capabilityClasses, verificationLevel, reasons, approvalRequired, fallbackPolicy, escalationTriggers}`. Leave `detect_capability()` and the `detect`/`fallback` subcommands unchanged so `v016-capability-detector-regression.sh` continues to pass. The classifier must not activate any provider — it only records `approvalRequired` entries; activation stays in `lazybuddy_capability.py`.
- **Tests that must not break:** `lazybuddy-plugin/tests/v016-capability-detector-regression.sh`, `v016-capability-broker-regression.sh`, `v016-tooling-policy-regression.sh`, `v017-capability-readiness-contract-regression.sh`, `v017-capability-readiness-regression.sh`, `v016-automatic-tooling-contract-parity.sh`, `lazybuddy-plugin/scripts/lazybuddy-contract-check.sh`.

### 2. Workflow selection
- **Files:**
  - `lazybuddy-plugin/agents/lazybuddy-orchestrator.md` (Sisyphus — root workflow coordinator)
  - `lazybuddy-plugin/commands/lazy-ultrawork.md` + `lazybuddy-plugin/skills/lazy-ultrawork/SKILL.md` (PIN→RED→GREEN→SURFACE→CLEAN)
  - `lazybuddy-plugin/commands/lazy-ulw-plan.md`, `lazy-start-work.md`, `lazy-ulw-loop.md`, `lazy-review-work.md`, `lazy-verifier.md`, `lazy-resume.md`, `lazy-new-run.md`, `lazy-status.md` (14 commands total)
  - `lazybuddy-plugin/skills/lazy-ulw-plan/`, `lazy-start-work/`, `lazy-ulw-loop/`, `lazy-review-work/`, `lazy-verifier/`, `lazy-ultrawork/`, `lazy-init-deep/`, `lazy-librarian/`, `lazy-migration-planner/`, `lazy-debugging/`, `lazy-programming/`, `lazy-git-master/`, `lazy-remove-ai-slops/`, `lazy-reviewer/` (14 skills)
  - `lazybuddy-plugin/agents/lazybuddy-{orchestrator,planner,explorer,implementer,verifier,reviewer,qa-executor,security-auditor,gate-reviewer,context-indexer,context-miner,librarian,migration-planner}.md` (13 agents)
- **Current behavior:** Workflow selection is **user-driven**. The user explicitly invokes one of the 14 `/lazy-*` commands or names a workflow in their prompt; the `UserPromptSubmit` hook (`scripts/hooks/user-prompt-submit.sh`) injects the matching skill bootstrap (e.g., ultrawork keyword → `ULTRAWORK MODE ENABLED!`). The orchestrator agent (Sisyphus) is invoked when the user says "start work", "execute plan", "continue plan", or references a `.lazybuddy/plans/` plan; it then dispatches implementer/verifier subagents but never selects a workflow mode itself — the workflow is already chosen by the time it runs. There is **no automatic mode selection** today.
- **Extension strategy (W3.2):** Introduce a thin LazyBuddy adaptive adapter module (e.g., `lazybuddy-plugin/tooling/lazybuddy_adaptive.py`) that consumes the Section 5 decision from the extended detector (seam 1) and maps each mode onto existing surfaces:
  - `direct` → no skill, direct Edit + targeted verification via `lazy-verifier` skill
  - `assisted` → `lazy-init-deep` or `lazy-librarian` for exploration + `lazy-debugging` if diagnostic + implementer agent + `lazy-verifier`
  - `planned` → `lazy-ulw-plan` skill + `lazy-start-work` skill + `lazy-verifier`
  - `orchestrated` → `lazybuddy-orchestrator` agent (Sisyphus) + `lazybuddy-security-auditor`/`lazybuddy-reviewer` for independent review + `lazybuddy-verifier`
  - `long-horizon` → `lazy-ulw-plan` + `lazy-ulw-loop` skill + `lazybuddy-orchestrator` for continuation
  - Explicit user workflow requests (e.g., `/lazy-ultrawork`) remain authoritative per Section 6 step 1 — the adapter must NOT downgrade them; it may only add required verification/approval boundaries.
  - The adapter is invoked from a new thin intake path (no new command), or by extending the existing `user-prompt-submit.sh` hook to call the adaptive detector when no explicit `/lazy-*` command was recognized. Static command/hook/Skill/agent registrations stay unchanged.
- **Tests that must not break:** `lazybuddy-plugin/tests/v015-consumer-agents-regression.sh`, `v018-coupled-work-contract-regression.sh`, `v018-post-tool-use-injection-regression.sh`, `v101-ci-suite-separation-regression.sh`, `v102-workbuddy-package-preparation-regression.sh`, plus the hook-pipeline test.

### 3. Provider/tool resolution
- **Files:**
  - `lazybuddy-plugin/tooling/lazybuddy_policy.py` (approval ledger + provider status; CLI `providers`, `providers configure`, `providers test`, `approval grant|deny|revoke|check`, `setup`, `toolpack resolve`)
  - `lazybuddy-plugin/tooling/lazybuddy_policy_config.py` (config load/validate/write with `fcntl.flock` atomic writes; `contract_digest()`, `workspace_id()`, `valid_reference()`)
  - `lazybuddy-plugin/tooling/lazybuddy_capability.py` (capability broker; CLI `capability run`; resolves local providers, LSP, codegraph, remote providers via `LAZYBUDDY_PROVIDER_*_COMMAND` adapters; enforces `approval_decision` + `METERED_PROVIDERS` budget consent + `ALWAYS_ASK_ACTIONS`)
  - `lazybuddy-plugin/tooling/lazybuddy_capability_contract.py` (shared contract digest + `BrokerError`)
  - `lazybuddy-plugin/tooling/lazybuddy_capability_process.py` (subprocess runner with SIGTERM/SIGKILL timeout)
  - `lazybuddy-plugin/tooling/lazybuddy_capability_receipt.py` (toolpack receipt: `.lazybuddy-capability-receipt.json`, atomic `os.replace` writes)
  - `lazybuddy-plugin/tooling/lazybuddy_capability_readiness.py` (read-only 9-record readiness report; `READINESS_VERSION = "0.18.0"`; emits `package-ready | owned-ready | missing | incompatible | disabled | failed-optional | not-initialized`)
  - `lazybuddy-plugin/contracts/automatic-tooling-contract.v1.json` (contract v1.1.0: 9 providers, 9 capabilities, `fallbacks` chains, `automatic_provisioning` policy)
- **Current resolution order:** The broker `run()` in `lazybuddy_capability.py` first canonicalizes the capability, then branches: SAFE_CAPABILITIES (`local_search`, `structural_search`, `code_navigation`) go through `local_provider()` / `lsp_provider()` which try (1) host `shutil.which`, (2) receipt-owned `installed_provider()` under the toolpack, (3) install via `lazybuddy-tooling.sh`. Non-safe capabilities route through `remote_provider()` which checks `ALWAYS_ASK_ACTIONS`, then `approval_decision()` against the persisted ledger, then `METERED_PROVIDERS` budget consent, then the `LAZYBUDDY_PROVIDER_*_COMMAND` env-var adapter. `fallback_chain()` in the detector walks the contract's declared `fallbacks` (e.g., `code_navigation → structural_search → local_search`).
- **Fallback chains (from contract):**
  - `local_search` → (no fallbacks)
  - `structural_search` → `local_search`
  - `code_navigation` → `structural_search`, `local_search`
  - `architecture_search` → `code_navigation`, `structural_search`
  - `documentation_search` → `web_search`
  - `external_code_search` → `web_search`
  - `filesystem_read` → `local_search`
  - `web_search`, `browser_automation` → (no fallbacks)
- **Authority model:** `approval_decision()` returns `ask | allowed | denied` based on policy (`automatic | ask-once | always-ask`) and the persisted approval ledger. `provider_status()` exposes per-provider `decision` for the `providers` command. Read-only local providers (ripgrep, ast-grep, lsp, filesystem) are `allowed` by default; remote/metered providers (context7, grep_app, web, playwright, codegraph) require explicit approval.
- **Extension strategy (W3.2/W3.3):** Extend `lazybuddy_capability.py` with a new `resolve_capability_class(capability_class, decision, workspace)` function that implements the Section 9 resolution order (host-native → repo-native → system-local → package-owned ephemeral → optional provider → safe degraded → blocked). It must reuse `approval_decision()`, `METERED_PROVIDERS`, `ALWAYS_ASK_ACTIONS`, the existing toolpack receipt mechanism, and the existing `fallback_chain()` — no second provider lifecycle. Map the contract's `capabilityClasses` (`text-search`, `structural-search`, `semantic-navigation`, `architecture-context`, `documentation`, `execution`, `task-state`, `outcome-verification`) onto the existing 9 capabilities. When the preferred provider is unavailable, walk `fallback_chain()` and report the substitution in the adaptive snapshot's `runtimeResolution` field; never claim equivalent evidence when the fallback is weaker. CodeBuddy and WorkBuddy full-plugin mappings (W3.3) reuse the same broker — they differ only in plugin manifest and Skills/MCP discovery, not in capability resolution.
- **Tests that must not break:** `v016-capability-broker-regression.sh`, `v016-capability-detector-regression.sh`, `v016-tooling-policy-regression.sh`, `v016-tooling-lifecycle-regression.sh`, `v016-provider-lifecycle-regression.sh`, `v016-remote-capabilities-regression.sh`, `v016-lsp-regression.sh`, `v016-codegraph-regression.sh`, `v016-runtime-version-regression.sh`, `v016-package-onboarding-regression.sh`, `v017-capability-readiness-contract-regression.sh`, `v017-capability-readiness-regression.sh`, `v017-codegraph-*-regression.sh`, `v015-persistent-mcp-regression.sh`, `v015-mcp-path-boundary-regression.sh`, `v015-readiness-regression.sh`, `lazybuddy-contract-check.sh`.

- **Current behavior:** Multi-step work is coordinated by the Sisyphus orchestrator agent, which reads the plan from `.lazybuddy/plans/`, selects the next unchecked checkbox, dispatches implementer subagents in parallel bursts via the Agent tool, routes every DoneClaim to an independent `lazybuddy-verifier` (Oracle) subagent, merges approved evidence into the ledger, and marks checkboxes complete. The orchestrator NEVER writes product code — only `.lazybuddy/` state files. The ultrawork skill coordinates its own PIN→RED→GREEN→SURFACE→CLEAN loop with a binding reviewer gate for HEAVY-tier work. Hooks fire on lifecycle events but do not select workflows.
- **Extension strategy (W3.2):** The adaptive adapter (seam 2) becomes the **single intake point** that decides which orchestrator/skill to invoke. For `direct`/`assisted` modes, the adapter can hand off to a single implementer agent without invoking Sisyphus. For `planned`/`orchestrated`/`long-horizon` modes, the adapter hands off to Sisyphus with a pre-populated adaptive snapshot in `.lazybuddy/runs/<run_id>/state.json` (seam 5). Sisyphus continues to own subagent dispatch and evidence routing — the adapter does not spawn subagents itself. The `UserPromptSubmit` hook is the natural trigger point: when no explicit `/lazy-*` command is recognized, the hook calls the adaptive detector and routes to the selected mode's entry surface. No new hook is registered; the existing `user-prompt-submit.sh` is extended with a single branch. The Section 8 smallest-useful-team policy is enforced by the adapter's responsibility-to-agent mapping (one owner per stage; multiple specialists only for genuinely independent work).

  - `lazybuddy-plugin/agents/lazybuddy-verifier.md` (Oracle — independent read-only verifier; reproduces tests, probes 9 adversarial classes, returns `confirmed | false-positive | needs-fix | needs-human-review` with confidence ≥ 0.8)

  - `lazybuddy-plugin/skills/lazy-verifier/SKILL.md`, `lazy-review-work/SKILL.md`, `lazy-reviewer/SKILL.md`
  - `lazybuddy-plugin/scripts/loop/classify-failure.sh`, `create-repair-task.sh` (failure classification + repair task creation)

  - `lazybuddy-plugin/tests/v018-verifier-regression.sh`, `v015-verification-mcp-boundary-regression.sh`
- **Current behavior:** Task completion is verified at three levels: (1) the `lazybuddy-verifier` (Oracle) agent independently reproduces tests, runs Manual-QA scenarios, probes 9 adversarial classes, and returns a verdict with confidence; only `confirmed` allows checkbox completion. (2) The verification MCP server records gate results to `events.jsonl` and reads them back; `summarize_verification` produces a run-level summary. (3) `lazybuddy-verify.sh` is the master release gate that runs all package regressions. Failure classification goes through `loop/classify-failure.sh` and `create-repair-task.sh`.
- **Extension strategy (W3.5):** The adaptive harness does NOT replace the Oracle — it routes DoneClaims to it exactly as Sisyphus does today. The extension is:
  - The adaptive snapshot's `verificationLevel` field (`targeted | standard | independent | live-surface`) maps to existing verification depth: `targeted` → self-verification + `lazy-verifier` quick pass; `standard` → `lazy-verifier` full pass; `independent` → `lazybuddy-verifier` Oracle + `lazybuddy-reviewer`; `live-surface` → Oracle + Manual-QA channel capture per `lazy-ultrawork/SKILL.md`.
  - Bounded escalation (Section 12): when `targeted` verification fails, the adapter adds a `debug` stage and may escalate one mode level (e.g., `direct` → `assisted`); after two automatic escalations it writes a `blocked` state to the adaptive snapshot with `{reproduced failure, attempted approaches, current evidence, unresolved decision, exact next user decision}`. This reuses `loop/classify-failure.sh` and `create-repair-task.sh`.
  - Evidence freshness (Section 18): the adapter records a `revisionMarker` in the adaptive snapshot; the verifier rejects stale completion evidence when the revision marker has changed since the last verification. No new evidence-lineage database is introduced.
  - The verification MCP `summarize_verification` tool is extended to include adaptive snapshot status (mode, current stage, escalation count, blocker) when present.

## Risk callouts

- **No JSON Schema for run state today.** `lazybuddy-plugin/schemas/` contains only `.gitkeep`; validation is procedural in `validate-state.sh`. Adding the optional `adaptive` block requires extending `validate-state.sh` to accept the new field without breaking v1.0.2 state. A formal JSON Schema is recommended but optional; if added, it must accept v1.0.2 state as valid.
- **Single-writer is convention, not enforced.** Today, only the orchestrator writes `state.json` via the state scripts; there is no platform-level lock. The adaptive adapter must follow the same convention — a new `update-adaptive.sh` helper is the single write path for the `adaptive` block. The run-ledger MCP `update_task` tool already writes `state.json` via `update-task.sh`; a parallel `update_adaptive` MCP tool (if added) must delegate to `update-adaptive.sh`, not write directly.
- **No cross-process locking.** `lazybuddy_policy_config.py` uses `fcntl.flock` for the policy config file, but run-state scripts use mktemp+mv without flock. The adapter must NOT add flock or compare-and-swap to run state (Section 11 rule). Atomic replacement via mktemp+mv is the only mechanism.
- **Detector is first-match, not scoring.** `detect_capability()` is an ordered if/elif chain. The adaptive detector must follow the same style (Section 6 ordered policy) — no scoring engine, no weights, no ML classifier.
- **Hook script extension is delicate.** `user-prompt-submit.sh` is the natural intake point for adaptive selection, but it runs on every prompt with a 10-second timeout. The adaptive detector call must be fast (sub-second) and must not block explicit `/lazy-*` commands. The `v018-post-tool-use-injection-regression.sh` and `v101-ci-suite-separation-regression.sh` tests guard this boundary.
- **WorkBuddy full-plugin vs Skills/MCP-only.** The adapter must distinguish full-plugin WorkBuddy (all Skills, commands, agents, hooks, 6 MCP servers) from Skills/MCP-only fallback (degraded). The `lazybuddy-load-check.sh` script already emits `READINESS_SCOPE=manual-skills-mcp-fallback` for the degraded case — the adapter should respect this signal.
- **Contract digest coupling.** `lazybuddy_detector.py`, `lazybuddy_policy.py`, `lazybuddy_capability_contract.py`, and `lazybuddy_capability_readiness.py` all call `contract_digest()` against the same `automatic-tooling-contract.v1.json`. The new `adaptive-harness-contract.v1.json` is a **separate** contract with its own digest — it must not be confused with the existing v1.1.0 contract. The `lazybuddy-contract-check.sh` regression test must continue to validate the existing contract unchanged.
- **Test count is large.** LazyBuddy has 40+ regression scripts under `tests/` plus the master `lazybuddy-verify.sh` gate. Any change to detector, broker, state, or MCP scripts risks breaking multiple regressions. The W3 implementation must run the full `lazybuddy-verify.sh` suite after each sub-task and capture evidence in `.lazytrae/evidence/`.
- **Sisyphus is prose-enforced, not platform-enforced.** The orchestrator's "never write product code" rule is documented in `lazybuddy-orchestrator.md` but `disallowedTools: []` (known gap G-016). The adaptive adapter must not rely on platform enforcement of this boundary — it is a convention.
- **`AGENT_ATTRIBUTION.md` marker.** This worktree already has the W0.1 attribution marker committed (`6226f12`). The W0.3 change map commit must be a separate atomic commit on the same branch, not squashed with the marker.
