# LazyBuddy v1.0.3 migration guide

## Durable package boundary

LazyBuddy v1.0.3 requires **Node.js LTS 20 or newer** and **Git**. Bootstrap
`onboard` only from the verified official origin
`https://github.com/elvinzhao10/LazyBuddy.git` (or the equivalent URL without
`.git`). The source checkout is one-time transport and may be deleted after
promotion.

| Platform | Default install root | Evidence boundary |
| --- | --- | --- |
| macOS | `~/Library/Application Support/LazySeries` | Package behavior verified; host behavior still requires observation. |
| Linux | `${XDG_DATA_HOME:-~/.local/share}/lazyseries` | Package path implemented; host behavior unverified. |
| Windows | `%LOCALAPPDATA%\LazySeries` | Package path implemented; host behavior unverified. |

```text
<install-root>/
└── LazyBuddy/
    ├── active.json
    ├── launcher.js
    ├── releases/<version>-<12-char-commit>/
    ├── receipts/<receipt-id>.json
    ├── rollback/
    ├── staging/
    └── locks/
```

After onboarding, run `update`, `status`, and plan-first `offboard` through
`node "<install-root>/LazyBuddy/launcher.js"`. Do not restore source-relative,
PATH, temporary-directory, cache, or `--plugin-dir` launchers.

## Filesystem and platform limits

The package fixtures parse the Windows default
`%LOCALAPPDATA%\LazySeries`, including paths with spaces. On POSIX, tests use
real filesystem symlink and hardlink refusal fixtures. Case sensitivity and
maximum path length follow the current filesystem, so tests probe the host
capability and use bounded names rather than assuming macOS, Linux, and Windows
behave alike. These are package-safe fixture checks; this does not simulate
host readiness.

## v1.0.2 to v1.0.3

1. Inventory receipt-owned, modified, and unknown v1.0.2 assets.
2. Run durable `onboard` with absolute install and project roots.
3. Run `status`, then the release-local load-check and doctor. These prove
   package readiness only.
4. Select one host route. CodeBuddy uses its documented marketplace route;
   WorkBuddy uses Skills import plus six manual MCP connectors.
5. Ask before each host mutation. Give one GUI/host action, wait, and inspect.
   Reload/new session and live verification are later actions.
6. Verify the route's Skill/command and all six MCP connections. Without
   current observation, **HOST READINESS: PENDING**.

Historical WorkBuddy feedback described full-plugin behavior after
undocumented host-internal changes. It is evidence about one supplied build,
not an installation contract. Never reproduce private host state; use the
supported fallback.

## Update identity and rollback retention

`update` resolves the official ref to a full commit SHA. A tag name is not
immutable identity. If a same-version ref moves, review
`required_confirmation`, then repeat with `--confirm-revision <full-sha>` only
for the intended commit.

One verified previous bundle may be retained. It is recovery evidence, not a
public hand-edit surface. Never alter `active.json`, `rollback/`, or receipts.
Preserve blocked, modified, unknown, or locked state and report the exact issue.

## Node runtime refresh

The receipt fingerprints the exact Node executable. If Node moves, is replaced,
or is upgraded in place, `status` reports `STALE_RUNTIME`; it does not silently
select PATH. Use a fresh checkout from the verified official origin to:

1. run `offboard` without `--yes` and review the exact product-only plan;
2. repeat with `--yes` after confirmation; and
3. run `onboard` with the current Node.js LTS runtime.

Project and host state remain outside this refresh. Re-run package checks, then
refresh/restart the host as separate one-action handoffs.

## Scoped offboard

`offboard` removes only exact receipt-owned LazyBuddy state. It refuses
modified, unknown, linked, locked, or incomplete product content. It does not
remove the project, LazyTrae, marketplace/Skills entries, MCP connectors,
credentials, or host state.

Remove the selected host route through its own documented UI after separate
approval. Observe a fresh session before reporting host removal. Package
removal and historical QA never make the current host ready.
