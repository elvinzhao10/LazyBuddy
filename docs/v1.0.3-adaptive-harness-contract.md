# v1.0.3 Adaptive Harness Contract

The adaptive harness contract is the behavior-only shared specification that
introduces adaptive workflow selection in the v1.0.3 release. A user states an
outcome; the harness selects the smallest sufficient workflow mode, composes
existing Skills, agents, commands, MCPs, tools, hooks, and verifiers, persists
an additive single-writer snapshot, and explains material choices. The contract
is shared byte-identically by LazyTrae and LazyBuddy. Each runtime maps it onto
its own surfaces; the contract never names them.

This document is the source of truth for what the contract means, how to
validate it, and how it stays byte-identical across repositories. It does not
document host-internal names. For the smallest-seam integration plan in each
repository, see [v1.0.3 Change Map](v1.0.3-change-map.md).

## Overview

Before v1.0.3, LazyTrae and LazyBuddy each offered a menu of named workflows
(`lazy-ulw-plan`, `lazy-start-work`, `lazy-review-work`, `lazy-ulw-loop`, and
related surfaces). A user had to pick the workflow. v1.0.3 keeps every named
workflow authoritative and adds an adaptive layer that selects the smallest
sufficient mode for ordinary outcome-based requests.

The contract exists to:

- Normalize an outcome request into a deterministic decision: mode, stages,
  responsibilities, capability classes, verification level, reasons, approval
  boundaries, escalation rules.
- Keep the decision policy small and ordered rather than an opaque scoring
  engine.
- Preserve runtime independence: LazyTrae and LazyBuddy must not import, call,
  or depend on each other at runtime.
- Keep host-internal names (Skill, agent, MCP, hook, command) out of the shared
  contract. Each runtime resolves them independently.
- Make authority explicit: read-only and package-owned capabilities activate
  automatically; installations, credentials, host settings, and remote access
  require approval.
- Keep state additive and backward-compatible: existing v1.0.2 state must
  continue to load.

The contract is deliberately behavior-only. It does not describe how either
repository implements detection, mapping, state writes, or explanation output.
It describes what the user-visible decision must be.

## Contract structure

The contract file is `adaptive-harness-contract.v1.json`, paired with its JSON
Schema `adaptive-harness-contract.v1.schema.json` and a sha256 digest file. In
LazyTrae it lives under
`lazytrae-plugin/packages/cli/contracts/`. In LazyBuddy it lives under
`lazybuddy-plugin/contracts/`.

The top-level fields are:

| Field | Purpose |
| --- | --- |
| `$schema` | Identifies the JSON Schema file that validates this contract. |
| `contract_version` | Locked to `"v1"` for the v1.0.3 release. |
| `modes` | The five workflow modes and their required behavior, capabilities, responsibilities, approval flag, and workflow surfaces. |
| `decision_policy` | The ordered seven-step resolution algorithm that selects a mode. |
| `snapshot_schema` | The shape of the additive `adaptive` block written to existing run/loop state, plus the single-writer rule. |
| `authority_matrix` | Per-responsibility authority level (`automatic` or `approval-required`). |
| `escalation_bounds` | Maximum number of automatic depth escalations and the triggers that may cause them. |
| `transparency` | Which selected and not-selected fields must appear in the user-facing explanation. |

The schema marks every top-level field as required and forbids additional
properties, so any future contract change must amend the schema and bump the
contract version.

## Modes

The contract defines five modes. The harness selects the lowest mode that
satisfies all identified risk, uncertainty, continuation, and verification
requirements.

| Mode | When to use | Approval required |
| --- | --- | --- |
| `direct` | Localized change, clear acceptance criteria, targeted verification is sufficient. No plan artifact or subagent by default. | No |
| `assisted` | Unfamiliar repository or subsystem, cross-file symbol tracing, primarily debugging, or bounded implementation that needs exploration or one specialist responsibility. | No |
| `planned` | Acceptance criteria incomplete; change spans multiple systems or architectural boundaries; important decisions must be resolved before editing; scope is broad but does not require a multi-agent team. | No |
| `orchestrated` | Security-sensitive behavior; release or publication behavior; installation or configuration ownership; destructive migration; two or more genuinely independent implementation workstreams; explicit independent review requirement; user-visible integration where failure would be materially costly. | Yes |
| `long-horizon` | Request explicitly requires multi-session work, durable checkpoints, repeated cycles, or a bounded continuation loop. Uses the existing loop/run-state machinery. | No |

Each mode declares:

- `description` — the behavior the harness must implement when selecting this
  mode.
- `approval_required` — whether the harness must request approval before
  executing.
- `capabilities` — capability classes the mode is allowed to use.
- `responsibilities` — named responsibilities engaged for the mode.
- `workflow_surfaces` — named workflow surfaces (e.g. `lazy-ulw-plan`,
  `lazy-start-work`, `lazy-ulw-loop`, `lazy-review-work`) the mode may use.
  These are workflow names, not host-internal provider names; each runtime
  resolves them to its own surfaces.

Mode controls depth. It does not prescribe exact agents or provider names.

## Decision policy

The `decision_policy.steps` array contains exactly seven ordered steps. The
harness evaluates them in order and selects the first match. The tie-breaking
rule is: choose the lowest mode that satisfies all identified risk,
uncertainty, continuation, and verification requirements. Do not select a
deeper mode simply because more capabilities are available.

In plain language:

1. **Explicit user workflow** — A named workflow or explicit instruction is
   authoritative. The classifier may add required verification or approval
   boundaries but must not silently downgrade or replace the explicit request.
2. **Compatible continuation** — When a compatible adaptive snapshot exists,
   resume the existing mode and current stage. Do not re-plan from the
   beginning. Reclassify only when the repository revision, request, scope, or
   host capability changed materially.
3. **Long-horizon work** — Select `long-horizon` when the request explicitly
   requires multi-session work, durable checkpoints, repeated cycles, or a
   bounded continuation loop. Use the existing loop/run-state machinery.
4. **High-risk or multi-system work** — Select `orchestrated` when one or more
   of these apply: security-sensitive behavior; release or publication
   behavior; installation or configuration ownership; destructive migration;
   two or more genuinely independent implementation workstreams; explicit
   independent review requirement; user-visible integration where failure
   would be materially costly.
5. **Broad or ambiguous work** — Select `planned` when acceptance criteria are
   incomplete; the change spans multiple systems or architectural boundaries;
   important implementation decisions must be resolved before editing; scope is
   broad but does not require a multi-agent team.
6. **Unfamiliar, cross-file, or diagnostic work** — Select `assisted` when the
   repository or subsystem is unfamiliar; cross-file symbol tracing is
   required; the request is primarily debugging; implementation is bounded but
   needs exploration or specialist verification.
7. **Small, clear, low-risk work** — Select `direct` when the change is
   localized, acceptance criteria are clear, and targeted verification is
   sufficient.

Each step records its `inputs` (signals the classifier must read) and `outputs`
(decision fields the step produces). The schema enforces `minItems: 7` and
`maxItems: 7`, so the policy cannot grow silently.

## Snapshot schema

The `snapshot_schema` block defines the additive `adaptive` block that the
harness writes inside existing run/loop state. It is optional and
backward-compatible: v1.0.2 state without the `adaptive` block must continue to
load.

The schema lists 14 required fields:

| Field | Type | Purpose |
| --- | --- | --- |
| `version` | integer | Adaptive snapshot schema version (currently `1`). |
| `decisionId` | string | Unique identifier for the adaptive decision. |
| `requestDigest` | string | Digest of the original user request for compatibility checking. |
| `mode` | string | Selected workflow mode. |
| `stages` | array | Ordered list of stages selected for this decision. |
| `currentStage` | string | Current active stage. |
| `responsibilities` | array | Named responsibilities engaged for this decision. |
| `capabilityClasses` | array | Capability classes required for this decision. |
| `runtimeResolution` | object | Mapping of capability class to resolved provider. |
| `reasons` | array | Material reasons for the selected mode and omissions. |
| `escalationCount` | integer | Number of automatic depth escalations applied (bounded by `max_auto_escalations`). |
| `revisionMarker` | string | Repository revision marker for compatibility checking on resume. |
| `blocker` | null or string | Current blocker, or `null` when not blocked. |
| `nextAction` | string | Next action to take in the current stage. |

**Single-writer rule.** The `single_writer` field is fixed to `"orchestrator"`.
Only the adaptive orchestrator writes the `adaptive` block. Skills, agents,
hooks, and MCPs may read the snapshot or return results to the orchestrator;
they must not mutate it directly. The harness uses the existing atomic-write
mechanism in each repository. v1.0.3 does not add cross-process locking,
compare-and-swap, or a new mutation API.

**Resume and stale-snapshot rules.** A snapshot is resumable only when its
request digest and revision marker remain compatible. When incompatible, the
harness marks it stale, preserves it for diagnosis, and produces a new
decision. A stale snapshot cannot establish completion. Unknown future adaptive
fields must be preserved where the current state mechanism supports
preservation.

## Authority matrix

The `authority_matrix` field maps each named responsibility to one of two
authority levels: `automatic` or `approval-required`.

| Responsibility | Authority |
| --- | --- |
| `continuity` | automatic |
| `debugging` | automatic |
| `exploration` | automatic |
| `implementation` | automatic |
| `planning` | automatic |
| `quality-review` | automatic |
| `release-review` | approval-required |
| `security-review` | approval-required |
| `verification` | automatic |

In plain language:

- **Automatic authority** covers already-loaded host/plugin capabilities,
  repository files and commands, read-only local inspection, compatible
  system-local tools, package-owned ephemeral providers already permitted by
  the existing lifecycle, and package-owned MCP processes already declared for
  the runtime.
- **Approval-required authority** covers downloading or installing a
  dependency; persisting a provider beyond the task; modifying host or
  marketplace settings; changing MCP registrations; using credentials; using a
  paid or authenticated service; sending repository data to a remote provider;
  controlling a browser or desktop surface; making an account, marketplace, or
  external-service mutation.

The two approval-required responsibilities (`release-review` and
`security-review`) gate the `orchestrated` mode. The harness must request
approval before performing them.

## Escalation bounds

The `escalation_bounds` block defines deterministic, bounded escalation.

- `max_auto_escalations` is fixed to `2`. No more than two automatic depth
  escalations are permitted for one decision.
- `escalation_triggers` lists the five conditions that may cause an automatic
  escalation:

| Trigger | Effect |
| --- | --- |
| `verification_failure` | A targeted verification failure adds a debugging stage. |
| `broader_scope_revealed` | A failure that reveals broader scope may increase the mode by one level. |
| `new_risk_finding` | A new security, release, migration, or destructive-risk finding requires independent review. |
| `capability_unavailable` | An unavailable capability uses a fallback before increasing workflow depth. |
| `user_goal_changed` | A changed user goal produces a new decision rather than mutating the old goal invisibly. |

**Blocked state.** Repeated failure after the bound produces a blocked state.
The blocked-state record must contain: reproduced failure; attempted
approaches; current evidence; unresolved decision; exact next user decision or
external requirement. The harness must not loop indefinitely or create a
growing repair lineage system in v1.0.3.

Escalation is bounded by the same `max_auto_escalations=2` constant for every
fixture, so the bound is part of the contract, not a runtime configuration.

## Transparency

The `transparency` block names which fields the user-facing explanation must
include.

**Selected fields** (must appear in the explanation):

- `mode`
- `stages`
- `responsibilities`
- `capabilities`
- `approval_required`

**Not-selected fields** (must appear as explicit omissions with reasons):

- `architecture-context`
- `external-code-search`
- `independent-review`

The explanation extends an existing status, capability, or run-state surface.
v1.0.3 does not add a new command for explanation. The explanation should
describe material choices, not expose internal routing noise. A representative
explanation:

```
Mode: Planned
Selected stages:
- repository understanding
- implementation plan
- implementation
- outcome verification
Responsibilities:
- exploration
- implementation
- verification
Capabilities:
- host-native text search
- semantic navigation
- package verification
Not selected:
- architecture graph: unnecessary for current scope
- external code search: no external example required
- independent review: task is not material risk
Approval required:
- none
```

## Fixtures

The shared fixture set lives under `contracts/fixtures/v103/` in both
repositories. Each fixture is a JSON file with a representative request, the
context signals the classifier should observe, the expected decision, the
expected snapshot, adversarial checks, and the permitted escalation. The
fixture set is documented by `manifest.json` and verified by `sha256sums.txt`.

The ten fixture categories:

| # | Fixture | One-line description |
| --- | --- | --- |
| 01 | `direct-localized-fix` | Localized one-file behavior correction selecting `direct` with targeted verification only. |
| 02 | `assisted-cross-file-bug` | Unfamiliar cross-file bug selecting `assisted` with exploration, debugging, implementation, and verification. |
| 03 | `planned-broad-feature` | Broad feature with unresolved design choices selecting `planned`; planning must precede product edits. |
| 04 | `orchestrated-security-change` | Security-sensitive authorization change selecting `orchestrated` with implementation, security review, and independent verification. |
| 05 | `orchestrated-release` | Release or publication change selecting `orchestrated` with release responsibility and publication evidence. |
| 06 | `long-horizon-migration` | Multi-session migration selecting `long-horizon` with the existing continuation loop and a resumable adaptive snapshot. |
| 07 | `explicit-workflow-override` | Explicit named workflow that remains authoritative; classifier does not silently downgrade. |
| 08 | `preferred-provider-unavailable` | Preferred provider unavailable; preserve mode, select allowed fallback, explain weaker evidence. |
| 09 | `escalation-bound` | Direct task that fails verification and reveals broader scope; escalates once, then produces a bounded blocked state at `max_auto_escalations=2`. |
| 10 | `responsibility-ownership` | Orchestrated mode with genuinely independent workstreams; one owner per stage, no duplicated work. |

Each fixture defines: required mode; required and forbidden stages; required
responsibilities; required capability classes; allowed provider substitutions;
approval expectations; verification level; permitted escalation. Fixtures do
not embed runtime calls and do not couple to host-specific providers.

## Validation

The contract is validated at two layers: schema validation of the contract
itself, and contract validation of fixtures.

**Contract against its schema.** The contract file declares
`"$schema": "adaptive-harness-contract.v1.schema.json"`. Validate with any
JSON Schema draft-07 validator. Using `ajv` CLI as the reference validator:

```bash
ajv validate -s adaptive-harness-contract.v1.schema.json \
  -d adaptive-harness-contract.v1.json
# Expected: exit 0, no errors
```

The schema enforces:

- All seven top-level fields are required; no additional properties.
- `contract_version` is the const `"v1"`.
- `decision_policy.steps` has exactly seven entries.
- `escalation_bounds.max_auto_escalations` is the const `2`.
- `escalation_bounds.escalation_triggers` has at least five entries.
- `snapshot_schema.single_writer` is the const `"orchestrator"`.
- `snapshot_schema.fields` has at least 14 entries.
- `modes` requires all five modes (`direct`, `assisted`, `planned`,
  `orchestrated`, `long-horizon`).
- `authority_matrix` requires all nine responsibilities.

**Fixtures against the contract.** Each fixture's `expected_decision.mode`
must be one of the five modes the contract declares. Each fixture's
`expected_snapshot.adaptive` block must satisfy the 14 required fields listed
in `snapshot_schema.fields`. Each fixture's
`permitted_escalation.max_auto_escalations` must be `<=` the contract's
`escalation_bounds.max_auto_escalations`. Each fixture's
`expected_decision.responsibilities` must be a subset of the keys in
`authority_matrix`. Adversarial checks listed in each fixture must be
enforced by negative tests in each runtime.

**Digest validation.** Each contract file has a paired `.sha256` digest. Each
fixture set has a paired `sha256sums.txt`. Verify with:

```bash
shasum -a 256 -c adaptive-harness-contract.v1.json.sha256
# Expected: OK
shasum -a 256 -c contracts/fixtures/v103/sha256sums.txt
# Expected: 10 OK lines
```

## Cross-repo byte-identical requirement

LazyTrae and LazyBuddy must carry byte-identical copies of:

- `adaptive-harness-contract.v1.json`
- `adaptive-harness-contract.v1.schema.json`
- `adaptive-harness-contract.v1.json.sha256`
- Every fixture under `contracts/fixtures/v103/`
- `contracts/fixtures/v103/manifest.json`
- `contracts/fixtures/v103/sha256sums.txt`

The two repositories live at:

- LazyTrae: `lazytrae-plugin/packages/cli/contracts/`
- LazyBuddy: `lazybuddy-plugin/contracts/`

Verify byte-identical status with:

```bash
diff \
  /path/to/lazytrae/lazytrae-plugin/packages/cli/contracts/adaptive-harness-contract.v1.json \
  /path/to/lazybuddy/lazybuddy-plugin/contracts/adaptive-harness-contract.v1.json
# Expected: empty diff
diff -r \
  /path/to/lazytrae/lazytrae-plugin/packages/cli/contracts/fixtures/v103/ \
  /path/to/lazybuddy/lazybuddy-plugin/contracts/fixtures/v103/
# Expected: empty diff
```

The contract is intentionally behavior-only. It contains no host-internal
names, so byte-identical vendoring is achievable without sacrificing runtime
independence. The two repositories never import, call, or depend on each other
at runtime; they share only the versioned contract, fixtures, digest, and
documentation artifacts.

## Versioning

The contract version is `"v1"` and is locked for the v1.0.3 release. The
`contract_version` field is a schema const, so any change requires a new
contract file (for example, `adaptive-harness-contract.v2.json`) and a
corresponding schema bump.

The fixture set is identified by `fixture_set: "v103"` in `manifest.json` and
lives under the `v103/` directory. A future release that adds, removes, or
changes fixture expectations must use a new fixture-set directory and update
`manifest.json` and `sha256sums.txt` together.

The adaptive snapshot carries its own `version: 1` integer inside the
`adaptive` block. This is independent of the contract version and the host
package version. The host package version is bumped separately to `1.0.3` on
all authoritative surfaces (AGENTS.md managed block, `package.json`, plugin
manifests, CLI banner, generated config templates).

Anything outside the contract, fixtures, digest, and documentation — including
detector normalization, runtime mapping adapters, snapshot extension hooks,
explanation surfaces, and tests — is implementation owned by each repository
and is not required to be byte-identical across repositories. Parity tests
compare user-level behavior classes (selected mode, required stages,
responsibilities, capability classes, approval boundaries, escalation
conditions, verification level, final success or blocking semantics), not
internal names.

## Evidence labels

The adaptive harness draws a strict line between four kinds of evidence.
Documentation, status output, and release claims must keep these labels
distinct. A result of one kind is never promoted to a stronger kind without an
explicit observation that supports the promotion.

| Label | What it proves | What it does **not** prove |
| --- | --- | --- |
| **package evidence** | Files in the pinned release, the generated declaration, contract digest parity, fixture schema validation, and local contract checks (`lazybuddy-load-check.sh`, `lazybuddy-plugin-doctor.sh`, `lazybuddy-verify.sh`, contract/fixture digest tests). | Plugin discovery, hook execution, a running session, or an MCP connection in any host. |
| **parity evidence** | LazyBuddy and LazyTrae consume byte-identical contract, schema, fixtures, and digest; equivalent fixtures produce equivalent user-level decisions (mode, stages, responsibilities, capability classes, approval boundaries, escalation conditions, verification level). | Identical internal names, exact Skill/MCP/hook wiring, host-internal routing, or any live-host behavior. |
| **observed-build evidence** | Behavior observed in one specific recorded host build (e.g. WorkBuddy v5.2.6 on macOS dated 2026-07-18, CodeBuddy IDE on macOS dated 2026-07-18). Recorded with exact product name, version, build, platform, and architecture. | That the same behavior will reproduce in a different build, on a different platform, or after a host update. It is not a public compatibility promise. |
| **live-host evidence** | A fresh, currently observed host session that shows the requested Skill/command and every expected MCP connection for the selected route. | Anything outside that observed session, including future sessions, other hosts, or other projects. Without current observation, the host route is **PENDING**. |

**Default state.** Package checks produce `package evidence` only. Parity tests
produce `parity evidence`. A past recorded build observation is `observed-build
evidence` for that build only. The current live-host status for WorkBuddy
full-plugin (W5.3), CodeBuddy full-plugin (W5.4), and the Skills/manual-MCP
fallback is **PENDING** because no live host was available in this release
session. The supplied macOS QA from 2026-07-18 is `observed-build evidence`,
not live-host proof.

The harness output, status surfaces, and release documentation must never
blur these labels. A passing local contract test is `package evidence`; it
does not become `live-host evidence` by repetition or by being mentioned in a
release note.

## Known v1.0.3 gaps

The v1.0.3 release is intentionally surgical. The following items are part of
the contract surface but are **not fully implemented** in this release. They
are documented honestly so users, reviewers, and the next release do not infer
behavior that is not present.

### W4.5 — Compatible continuation resume (deferred to v1.0.4)

The contract's decision policy step 2 (`compatible_continuation`) specifies
that when a compatible adaptive snapshot exists, the harness resumes the
existing mode and current stage rather than re-planning from the beginning,
and that reclassification happens only when the repository revision, request,
scope, or host capability changed materially.

**v1.0.3 state:** the classifier in
`lazybuddy-plugin/tooling/lazybuddy_adaptive_detector.py` does **not** read
`context['snapshot']` to implement step 2. It always produces a fresh
decision. The persistence layer preserves a stored snapshot for diagnosis (it
is not mutated or deleted), and a stale snapshot is not accepted as completion
evidence, but the harness does not yet resume an in-flight session from the
saved stage. The W4.5 test file
(`lazybuddy-plugin/tooling/test_lazybuddy_adaptive_w4_5_continuation.py`)
records this gap explicitly with `@pytest.mark.xfail` cases for the three
compatible-resume scenarios. Compatible continuation resume is deferred to
v1.0.4.

### W4.6 — Evidence freshness / stale-snapshot detection (deferred to v1.0.4)

The contract's snapshot schema carries a `revisionMarker` field for
compatibility checking on resume. Plan Section 18 requires that a stale
snapshot trigger reclassification rather than silent resume.

**v1.0.3 state:** the classifier emits a constant `revisionMarker: 'git:HEAD'`
string and does not derive a real revision marker from the repository or from
implementation content. Stale-snapshot detection (comparing the recorded
`revisionMarker` against the current marker to trigger reclassification) is
**not implemented**. The W4.6 test file
(`lazybuddy-plugin/tooling/test_lazybuddy_adaptive_w4_6_evidence_freshness.py`)
records two `xfail` cases for stale reclassification and re-verification
signalling. The `lazy-verifier` skill and existing publication-regression
checks still reject non-existent evidence paths and missing contract digests,
which prevents one class of stale-evidence completion, but it is not a full
freshness check. Stale-snapshot detection and re-verification signalling are
deferred to v1.0.4.

### W5.3 / W5.4 — Live-host QA (PENDING)

No live WorkBuddy, CodeBuddy, or other supported host was available during
this release session. Live-host adaptive behavior — observing one real
Skill/command, every expected MCP connection, the adaptive explanation, failure
escalation, and continuation through the current host surface — is **PENDING**.
Package and parity evidence are complete; observed-build evidence from the
2026-07-18 macOS QA remains valid for those specific builds (WorkBuddy v5.2.6
and CodeBuddy IDE on macOS); live-host evidence must be captured in a future
session with exact-build metadata before any host route can be marked
OBSERVED.
